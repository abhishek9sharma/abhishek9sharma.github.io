llm-d: many vLLMs working as a team

vLLM (Step 9) runs one model well on one machine. A real service runs many copies on a cluster, and then two new questions appear: which copy should get this request? and should every copy do both phases of the job? llm-d is an open-source project, led by Red Hat with partners, that answers them on top of vLLM. We keep following "The king sat on the ___".

Builds on Step 7 (prefill vs. decode) and Step 9 (blocks, prefix sharing). Some details of llm-d change quickly; where I could not verify a point it is marked as such.
01The Problem First

One vLLM per box is not a service

Picture three vLLM pods (a pod is Kubernetes' unit of running software; here, typically a vLLM server with one or more GPUs). A request arrives: a long shared system prompt followed by our question "The king sat on the". Two things go wrong with a naive setup:

1 · A plain load balancer ignores the cache. Step 9 showed prefix caching saves the work of re-reading a shared prompt — but each pod has its own cache. Send the request to a pod that has never seen the system prompt and you prefill it all again, even though another pod already holds it.
2 · Prefill and decode fight each other. Step 7: prefill pushes a whole prompt through at once (compute-bound); decode makes one token per step and waits on memory (memory-bound). On one GPU, a long prefill stalls everybody else's tokens.

llm-d keeps vLLM as the engine inside each pod (blocks, PagedAttention, continuous batching, prefix caching) and adds a coordinator around the engines:

Kubernetes / OpenShiftruns the pods llm-droutes requests, can split prefill from decode, keeps track of which pod holds which blocks vLLM (in each pod)blocks, PagedAttention, continuous batching, prefix caching GPUholds the model weights and the KV blocks

A pod may also hold helper containers; I did not verify llm-d's exact pod layout. llm-d is reported to run both vLLM and SGLang as model servers.

02Smart Routing

Send it where the blocks already are

Each pod reports to the router when it stores or drops a block, so the router keeps a global index of who holds what. For a new request it scores every pod by how many leading blocks the pod already has (cache) combined with how busy it is (load). Remember from Step 9: blocks are matched from the start and only full 16-token blocks count. Try it — the request is a 32-token system prompt (2 full blocks) plus our 5-token question (a partial block that cannot be matched yet):

Score(pod) = matching leading blocks (cache) + free capacity (load). Routing only on cache would pile everything onto one pod, so load is blended in. Events from pods can arrive a moment late, so now and then the router's picture is slightly out of date. Prefix-aware routing is not a vLLM feature (vLLM only caches inside one pod): choosing the pod is the router's job, which turns prefix caching from a per-machine trick into a cluster-wide one.
03Splitting The Phases

Prefill pods and decode pods

llm-d can run some pods only for prefill and others only for decode, and move the KV blocks from one to the other. Step through our request:

What does moving the cache cost?

The KV blocks of the prompt must be copied from the prefill pod to the decode pod (GPU memory to GPU memory over a fast network, using RDMA; llm-d uses NVIDIA's NIXL library for the transfer by default, as far as I could read). In the simple model above the copy and the prefill both grow in step with prompt length, so the share depends on the network and the model, not on the length (real prefill grows a little faster than linearly, which favours long prompts). What long prompts change is the stall: a long prefill sitting on a decode pod blocks every other request there, so splitting pays off with long prompts and heavy traffic, not short prompts on a small setup. Once decoding has started the request stays on its decode pod, and every later K and V lands in that pod's own blocks. The prefill pod may keep its blocks as prefix cache until it needs the space, then evicts the least recently used.
04What It Adds Up To

vLLM is the engine; llm-d is the coordinator

Smart routing — requests go where their prefix blocks already are.
Prefill/decode disaggregation — separate pods for the two phases, KV blocks moved between them.
Cache beyond the GPU — warm blocks in GPU memory, cooler ones in CPU memory or on disk (reported by the project).
Runs on Kubernetes or OpenShift — with vLLM and SGLang as supported model servers (reported by the project).

Claims about speedups come from each project's own benchmarks; test on your own traffic.
