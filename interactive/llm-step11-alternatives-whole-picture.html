SGLang, Ray Serve & the whole picture

Step 10 showed llm-d turning many vLLM engines into a service. But vLLM isn't the only engine, and llm-d isn't the only way to run engines as a cluster. This last step compares the alternatives, then walks "The king sat on the ___" → "throne" through every layer you have built, from text to pods.

Builds on Step 9 (prefix sharing by block hash) and Step 10 (llm-d). These projects change quickly; treat the finer points as a starting point, not a verdict.
01Another Engine

SGLang: the same goal, a different prefix index

SGLang is another open-source LLM engine, a direct alternative to vLLM: it also does continuous batching and prefix caching. The main difference is how it remembers prefixes. vLLM (Step 9) gives every full 16-token block a hash and matches block by block. SGLang keeps a radix tree of token sequences (RadixAttention), with the cached K and V attached to the tree nodes. A new prompt walks down the tree as far as it matches and reuses everything up to that point. Try it on a tree that already holds three earlier prompts:

02Another Way To Run Engines

Ray Serve: the same job as llm-d, by a different route

Ray is a general framework for distributed Python: a head node schedules and worker nodes do the work. Ray Serve is its serving layer: a model becomes a deployment with replicas that can be autoscaled, and a replica can run vLLM. Ray Serve LLM adds LLM-specific features, including prefill/decode disaggregation and a prefix-aware router. Both cover what Step 10 covered; the route differs:

llm-dRay Serve LLM

Rule of thumb: a team that already lives on Kubernetes and wants LLM-specific behaviour fits llm-d naturally; a team already using Ray for other workloads, or wanting one framework for many kinds of models, fits Ray Serve. Neither is a drop-in answer, and speed claims on both sides come from their own benchmarks — test on your own traffic. NVIDIA Dynamo is a third project in the same space; this series does not cover it and I have not checked how it compares.

Common mix-ups, settled

Real models differ in size, not in kind. Everything here was built from a 5-token toy. Llama-3.1-8B has 32 layers and 128 KiB of KV cache per token, and a real vocabulary has about 128,000 tokens. Every engine caches K and V; vLLM changed how that memory is organised; llm-d and Ray Serve spread engines over a cluster.
