The Memory Wall: why decoding is memory-bound

Step 7 showed the KV cache is essential. This step is the reality check: how big does it actually get, and where does it live? GPU memory is a strict hierarchy, and the KV cache eats it alive. This — not raw math — is what makes serving hard, and what the next tricks are built to fight.

Builds on Step 7 (the KV cache). Self-contained — the key facts are recapped as we go.
01The Intuition

Not short on math — short on memory

It's tempting to think a big model is slow because it does so much arithmetic. During generation, the opposite is often true. At small batch sizes, producing one token streams all the model's weights through the GPU and does very little compute per byte read. The GPU's math units sit half-idle, waiting for data to arrive from memory. That's what "memory-bound" means: the bottleneck is moving bytes, not multiplying them. (Not every phase works this way: prefill, which processes the whole prompt at once, is usually compute-heavy, and large batches shift decode toward compute too.)

Two things dominate that memory traffic: the model weights (streamed through for every step, shared by all requests in a batch) and the KV cache (read in full, every token, for every request in flight). Which one dominates depends on batch size, context length and the model. At short contexts the weights usually do; as contexts and concurrency grow, the KV cache becomes a major source of memory pressure. To see why, we need to look at where memory physically lives — and how much of it the cache demands.

02Where Memory Lives

The GPU memory hierarchy

GPU memory isn't one thing — it's a pyramid. As you go up it gets dramatically faster but smaller. The art of a fast kernel is keeping the data you're actively using as high up as possible. Click a tier to see what it's for.

Widths are scaled to relative capacity — SRAM is tiny, DRAM is vast. Numbers are rough, for an NVIDIA H100-class GPU; exact figures vary by chip.

Why this matters for attention: the KV cache lives in HBM (the green tier). Every attention step streams all of it up into SRAM to do the math. The bigger the cache, the more bytes cross that gap — every single token. Keep this picture in mind for FlashAttention below.

04Fighting Back

Two ways to beat the wall

The memory wall has two faces — bandwidth (moving the cache around) and capacity (fitting it at all). There's a landmark technique for each.

FlashAttention — the bandwidth fix

Naive attention builds the full N×N score matrix in HBM, then reads it back. FlashAttention never writes it down — it streams tiles through SRAM and computes softmax online. Same answer, a fraction of the memory traffic.

PagedAttention — how the cache is stored (next step)

Even with FlashAttention, the cache still has to fit. Store each request's cache as one contiguous block, reserved for the longest it might grow, and you can waste a large share of it to fragmentation and over-reservation (the PagedAttention paper measured 60–80% in the systems it compared; it depends on the workload). PagedAttention — the idea behind vLLM — borrows virtual memory from operating systems: chop the cache into small fixed pages and hand them out on demand. It does not shrink the K/V data; it wastes less of the space and makes sharing possible. That's Step 9 — we need its "request" and block-table vocabulary first, so here is just the headline.

05The Wider Toolbox

Other ways people shrink the wall

FlashAttention and PagedAttention are the headline acts, but production stacks pile on more. A quick tour of what else is out there — each deserves its own deep dive:

GQA / MQA
Grouped / Multi-Query Attention. Share one set of K/V across many query heads. Fewer KV heads → a directly smaller cache. You just saw this: Llama-3's 8 KV heads instead of 64.
Quantization
Store fewer bits. Weights and the KV cache don't need 16-bit floats — FP8 or INT8 roughly halve the memory (and the bandwidth) for the stored tensors, at some quality cost that depends on the method (scales and metadata add a little back). That 320 KB/token becomes roughly 160 KB.
Speculative
Speculative decoding. A small "draft" model proposes several tokens at once; the big model checks them together in one forward pass and keeps the ones it agrees with. More tokens per expensive memory read — attacking the bandwidth bound from another angle.
Prefix cache
Prefix / prompt caching (Step 9 shows how it works with blocks). Many requests share a long system prompt. Compute its KV once and reuse it across requests instead of re-prefilling every time.

Where this is heading

We've measured the wall: the KV cache is huge and it lives in scarce, fast memory. FlashAttention cut the bandwidth cost of using it. Step 9 tackles the capacity cost — how vLLM's PagedAttention packs many requests' caches into GPU memory without waste.
