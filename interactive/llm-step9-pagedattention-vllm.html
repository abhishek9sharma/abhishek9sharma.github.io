PagedAttention & vLLM: managing the cache

Step 7 introduced the KV cache; Step 8 showed it's enormous and hits a memory wall. Worse, its size per request grows and shrinks unpredictably — store it naively and you waste 60–80% of GPU memory. PagedAttention fixes this by borrowing the oldest trick in operating systems: paging. It's the core idea behind vLLM.

Builds on Step 7 (the KV cache) and Step 8 (its memory cost). Self-contained — the key facts are recapped as we go.
01The Waste

Why contiguous allocation bleeds memory

The naive approach: when a request arrives, reserve one contiguous block of memory big enough for the maximum sequence length it might reach — say 2048 tokens — even though it might only generate 30. This creates two kinds of waste:

First — what is a "request"?

A request is one user's call to the model: their prompt plus the tokens being generated back to them. A busy GPU serves many at once, and each one needs its own slice of KV-cache memory (the keys & values from Step 7). Throughout this page, R1–R4 are four such concurrent requests — each a different user, prompt, and length:

R1"Translate this email into French…" · short
R2"Write a haiku about the ocean…" · tiny
R3"Summarize this 5-page report…" · long
R4"def quicksort(arr): …" · medium

Each finishes at a different, unpredictable time — which is exactly what makes packing them into GPU memory hard.

The rest is reserved-but-empty (internal fragmentation) or unusable gaps (external fragmentation).
Two fragmentation types. Internal: each request reserves its max length but uses far less — the reserved-but-empty tail is dead memory for the request's whole lifetime. External: when a request finishes and frees its block, the gap may be too small or oddly-shaped for the next request's contiguous need. Real systems lose 60–80% of KV memory this way.
02The Idea

Paging: store the cache in small blocks, anywhere

Operating systems solved this for RAM decades ago. Don't demand one big contiguous chunk — split memory into fixed-size blocks (vLLM uses 16 tokens each) and let a sequence's blocks live anywhere, in any order. New tokens are the whole reason paging wins. During generation the model appends one token at a time to a request's KV cache (Step 7). With paging, a request holds only the blocks it has filled so far; when its last block fills up (every 16th token) it grabs one fresh block from the free pool — on demand. The naive scheme, by contrast, reserves a fixed slab up front. Hit a generate button and compare the panels: the paged side adds a block only at each 16-token boundary, while the naive side just fills (or overflows) its pre-reserved slab — try growing a boxed request (R1/R2) versus the last one (R3).
Waste is now bounded, not proportional. The only unused space is the partially-filled last block of each sequence — at most 15 tokens, no matter how long the sequence is. For this toy example (a handful of short requests), that bound is a real chunk of the total: –. But the bound stays fixed while real sequences run to hundreds or thousands of tokens — so in production the same 15-token cap shrinks to a couple of percent, versus the 60–80% naive contiguous allocation loses regardless of sequence length.
03Sizing The Pool

What's actually inside a block — and how many do you get?

You just saw paging beat fragmentation. Here's the catch: those blocks don't sit next to each other. vLLM drops each one into whatever slot is free, so a sequence's blocks scatter across the pool (blue = this prompt's blocks, grey = other requests', dashed = free — a small window into the pool):

So what stitches them back into one sequence? Each sequence keeps a tiny block table — an ordered list of the physical blocks it owns: logical block 0 first, then 1, and so on. It's exactly an OS page table.

04Bonus Win

Sharing blocks across requests

Yes — and it falls straight out of the block table. A table is just a list of pointers, so two requests that begin with the same tokens can point their first few entries at the same physical blocks instead of each storing a copy. That's prefix sharing.

But can one block mix two different requests' tokens? — No.

Sharing means two tables point at a block of identical content. A block is never split between two requests' different tokens. If a request fills only part of a block, the rest stays empty (that's the ≤15-token internal fragmentation) — those slots are not handed to another request:

✓ real one sequence · unused slots stay empty
✗ never mixing R1+R2 would make R1 attend to R2's tokens
Copy-on-write, exactly like an OS. As long as everyone only reads a shared block (a fixed system prompt, a RAG document, few-shot examples), it stays shared forever — pure savings. The moment one sequence needs to write a token into a shared block, vLLM copies just that one block first (refcount drops, a fresh block is allocated), so the others are unaffected. Prompts are read-only, so their blocks are typically never copied at all.
Why it compounds. Less memory per request → more requests fit at once → bigger batches → the GPU's tensor cores stay busy → higher throughput. Memory efficiency and speed are the same lever here.
05The Scheduler

Continuous batching keeps the GPU full

Flexible block memory unlocks one more win. Static batching groups N requests, runs them together, and waits for the slowest to finish before starting the next batch — so finished sequences leave the GPU idle. Continuous batching slots a new request into a free spot the instant one finishes. Compare:

PagedAttention turns KV-cache memory from the bottleneck that caps batch size into a non-issue, so a single GPU can serve far more concurrent users. It's why vLLM became the default open-source serving engine, and the technique now appears in nearly every production inference stack.

Source: Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention," SOSP 2023 (arXiv:2309.06180), and the vLLM project.
The trade-offs PagedAttention introduces ▾

Nothing is free. Paging adds a custom attention kernel that must gather K/V from non-contiguous blocks (a little slower per-op than a dense read), CPU bookkeeping to track thousands of block tables, and a preemption/swapping path for when the block pool runs out — evicting a sequence's blocks to CPU RAM and recomputing or swapping them back later, which causes latency spikes. In practice the memory win dwarfs these costs, which is why it's near-universal.
